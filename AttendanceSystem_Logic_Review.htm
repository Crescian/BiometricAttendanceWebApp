1. CSV Import & Attendance Processing

Controller: CsvimportController@uploadCSV
Service: AttendanceProcessor@processFile

1.1 File Upload & Validation

The user uploads a biometric export file (CSV or XLSX) through the web interface. Before processing, the controller resolves the currently-loaded biometric import session ID from the biometric_imports table (the row with status = 'load').

  • Accepted formats: .csv, .xls, .xlsx
  • The file is stored in a temporary upload directory.
  • A single $biometricImportId is used as the batch key for all records created from this file.

1.2 Reading the File

The service reads the file via readAttendanceFile().

For XLSX files:

  • Uses PhpSpreadsheet to load the workbook.
  • Skips the first two rows: Row 1 is the "Transactions" title row, Row 2 is the column header row.
  • Column mapping (A through K):
ColumnField
APersonnel ID
BFirst Name
CLast Name
DDepartment Name
EAttendance Area
FSerial Number
GAttendance Point Name
HAttendance time
IVerification Mode
JAttendance Photo
KData Sources

For CSV files:

  • Also skips the first two lines (title + header).
  • Uses the same 0–10 positional column mapping as above.

Attendance time normalization:

  • Primary format: n/j/Y g:i (e.g. 8/11/2025 7:00).
  • Falls back to Carbon::parse() for other formats.
  • Rows with an empty or unparseable Attendance time are silently skipped.

1.3 Grouping by Personnel ID

All rows are grouped by Personnel ID. Within each group, punches are sorted by Attendance time in ascending order. This gives each employee an ordered list of clock-in/clock-out timestamps for the day.

1.4 Punch Pairing Logic

Punch pairing converts raw timestamps into (earliest, latest) pairs per day. The algorithm differs for relievers vs. normal employees.

Reliever employees

Identified via employee_management.relievers = true.

  1. Punches are grouped by calendar date.
  2. For each date, the system looks for an evening punch (hour ≥ 12) on that date and a morning punch (hour < 12) on the next calendar date.
  3. If both are found → a NIGHT record is created with record_date = evening date.
  4. If no cross-day pairing is possible but ≥ 2 same-day punches exist → a DAY record (first punch = earliest, last punch = latest).
  5. If only 1 punch exists for a date → a SINGLE record (earliest = latest = that punch).

Non-reliever, night shift employees

Identified when the employee's normal schedule OR any of their temp adjustments is in the night-shift code list: 18-6, 19-7, 19-4, 20-5, 15-23, 15-24, 23-7, 23-8.

  1. Iterates all punches in order.
  2. When it finds a punch with hour ≥ 14 (not yet used), that becomes the start of a night shift block.
  3. Any subsequent punch within a 12-hour window of that start punch is included in the same block.
  4. The earliest punch in the block = earliest_time; the latest = latest_time.
  5. record_date = date of the earliest punch.

Non-reliever, day shift employees

  1. Punches are grouped by calendar date.
  2. Earliest punch of the day = earliest_time; latest punch = latest_time.
  3. If only one punch: earliest_time = latest_time (this record is later skipped at insert time).

1.5 Inserting Attendance Records

1.6 Post-Insert: Hours & OT Calculation

After all rows are inserted, calculateHoursForBiometricImport() runs over the newly inserted attendance_records rows to populate the overtimes table.

Hours worked

  • If the date is in custom_dates (non-working day) → hours_worked = 0.
  • Otherwise: seconds = latest_seconds - earliest_seconds (adds 86 400 if latest < earliest, i.e., crosses midnight).
  • Subtracts 1-hour break by default (hours = seconds/3600 - 1).
  • Exception: schedules 15-23 and 23-7 do not subtract the break.

Security department employees

If department = 'security' (case-insensitive), the computed hours are also written to the security_attendance table via logSecurityAttendance().

OT (simplified, initial pass)

  • ord_ot = max(hours_worked - 8, 0)
  • Night differential is calculated separately using secondsInNdWindow() (counts seconds in the 22:00–06:00 window).
Note: This initial pass is a simplified estimate. The detailed ND/OT breakdown (per-hour loop, late rule, RD detection) is performed later when OvertimeController@updateTime or a schedule adjustment approval re-triggers ComputationService::autocalculateOrd().

1.7 Non-Working Days Setup

The calculateTotalNonWorkingDays() method (called manually or on setup) populates the custom_dates table with:

  • All Sundays for the given year → holiday_type = 'Rest Day', title = Sunday Rest Day.
  • Philippine regular holidays (New Year, Maundy Thursday, Good Friday, etc.) → holiday_type = 'Regular Holiday'.
  • Philippine special non-working holidays (Chinese New Year, Ninoy Aquino Day, etc.) → holiday_type = 'Special Non-Working Holiday'.
  • If a holiday falls on a Sunday, its title gains the suffix "(Falls on Rest Day)".

2. Overtime Calculation

Controller: OvertimeController
Service: ComputationService

2.1 Overview

Overtime records are stored in the overtimes table. Each row links back to one attendance_records row via attendance_records_id. All OT/ND values are stored as HH:MM strings (e.g. "02:30"), never as decimal numbers.

2.2 Ordinary Day (ORD) Calculation – autocalculateOrd()

Step 1 – Early exit conditions

  • If record_date is in custom_dates (non-working day) → return [0, 0, 0].
  • If leaves = true → return [0, 0, 0].
  • If earliest_time is empty or equals latest_time → return [0, 0, 0].

Step 2 – Resolve schedule

The schedule (e.g. 8-17) is resolved in priority order:

  1. Check schedule_adjustments joined with employee_management for a matching employee name and exact record date (temp schedule takes priority).
  2. If no temp adjustment, use the employee's default schedule from employee_management.schedule.
  3. If no schedule found at all → return [0, 0, 0].

Step 3 – SG Vesta special case

If department is 'sg vesta' (case-insensitive), the schedule is auto-detected based on which of 07:00 or 19:00 is closer to the employee's earliest punch time:

if |earliest_seconds - 7*3600| ≤ |earliest_seconds - 19*3600|
    schedule = '7-19'
else
    schedule = '19-7'

Step 4 – Late rule

  • Parse the schedule start hour from the schedule string (e.g. 8 from "8-17").
  • Grace window: start_hour × 3600 + 15 × 60 seconds (i.e. 15 minutes after shift start).
  • If earliest_seconds > grace_window: set earliest_seconds = (start_hour + 1) × 3600 (shift the effective in-time forward by 1 hour from shift start).
Example: Schedule 8-17. Grace = 08:15. If employee punched in at 08:30, effective in-time becomes 09:00.

Step 5 – Midnight crossing

If latest_seconds ≤ earliest_seconds (punch-out is earlier than punch-in on the same calendar day), add 86 400 to latest_seconds to project it to the next day. This ensures night shift durations are always positive.

Step 6 – Hourly loop (ND and OT classification)

The work window is divided into 1-hour blocks. Each block is classified:

ndStartSec   = 22 × 3600   // 22:00
ndEndSec     = 6 × 3600    // 06:00
regularLimit = 8 × 3600    // 8 regular hours

worked = 0
current = earliest_seconds

while current < latest_seconds:
    next      = min(current + 3600, latest_seconds)
    blockSec  = next - current
    todSec    = current MOD 86400         // time-of-day within the 24-hour cycle
    isND      = (todSec ≥ 22*3600) OR (todSec < 6*3600)

    if worked < regularLimit:
        worked += blockSec
        if isND → ordNd += blockSec       // ND within regular 8 hours
    else:
        if isND → ordNdOt += blockSec     // ND overtime (after 8 hours, in ND window)
        else   → ordOt   += blockSec      // ordinary overtime (after 8 hours, outside ND)

    current = next

Results are returned as decimal hours (rounded to 2 places):

  • ord_ot – regular day overtime hours (non-ND, after 8 hrs)
  • ord_nd – night differential hours within regular 8 hrs
  • ord_nd_ot – night differential overtime (ND window, after 8 hrs)

2.3 Rest Day (RD) Calculation – autocalculateRdAndOvertime()

Trigger condition

This function only runs when record_date is found in custom_dates. If the date is a normal working day, it returns all zeros immediately.

RD base hours (schedule-dependent)

The RD base hours represent how many hours count as the "regular" rest-day portion before OT kicks in:

ScheduleRD Base HoursCondition
7-16, 8-17, 7-19, 6-15, 9-15, 10-18, 10-168Any punch-in time
15-246Punch-in hour ≥ 15
23-82Punch-in hour ≥ 23
23-71Punch-in hour ≥ 23
All other schedules (e.g. 18-6, 19-7)0 
Review point: Schedules 18-6, 19-7, etc. currently return rd = 0 because they are not in the day-shift list and do not match the three partial conditions above. Is this intentional?

RD hourly loop

Same approach as the ORD loop, but the regular threshold is 9 hours (8 hours regular + 1-hour break = 9 total before OT):

workedLimit = 9 × 3600

if worked < workedLimit:
    worked += blockSec
    if isND → rdNd += blockSec
else:
    if isND → rdNdOt += blockSec
    else   → rdOt   += blockSec

2.4 Writing to the Database – logOvertimeDb()

This method inserts or updates a row in the overtimes table. Matching (upsert) key:

employee_name + record_date + type + biometric_imports_id + attendance_records_id

If an existing record is found:

All OT values are stored as HH:MM strings:

toHM(hours) = sprintf('%02d:%02d', floor(hours), round((hours - floor(hours)) * 60))

2.6 Manual Time Edit – OvertimeController@updateTime()

When an admin edits the punch times for an OT record:

  1. Original times are preserved in original_earliest_time / original_latest_time (written only once; the first edit sets them; subsequent edits keep the original values).
  2. New times overwrite earliest_time / latest_time.
  3. autocalculateOrd() is called with the new times.
  4. autocalculateRdAndOvertime() is called.
  5. logOvertimeDb() upserts the result.

2.7 Night Differential (ND) Window

  • Window: 22:00 to 06:00 (next day).
  • ND is accumulated only for hours actually worked in this window.
  • Whether ND is within regular hours or OT depends on whether 8 regular hours have been exhausted.

2.8 Security Department – logSecurityDb()

For employees whose department is 'Security', a parallel record is written to security_attendance using the same punch times. The record stores hours_worked, ot, and nd separately and is matched by (employee_management_id, record_date, earliest_time, latest_time, biometric_imports_id).

3. Certificates of Attendance (COA)

Controller: CertificateOfAttendanceController
Table: certificate_attendance

3.1 Purpose

A Certificate of Attendance (COA) allows a manager to manually declare that an employee was present on a specific date (e.g., for days not captured by the biometric device). Once approved, it creates an official attendance_records entry for that employee and date.

3.2 Creating a COA – store()

Accepts an array of items (attendanceArray). Two modes:

Mode A – All Employees (employee_management_id = 'all')

  • Fetches every employee from employee_management.
  • For each employee, checks if a COA already exists for the same date with status Pending or Approved. If found → skips that employee and adds to the skipped list.
  • Creates a new COA record with approval_status = 'Approved' directly (bulk mode bypasses the Pending step).
  • Weekday is computed from the date using Carbon.

Mode B – Single Employee

  • Same duplicate check: blocks creation if a Pending or Approved COA exists for the same employee + date + biometric import.
  • Creates with approval_status = 'Pending' (requires explicit approval action).

Duplicate check scope

Checked on: employee_management_id + date + biometric_imports_id + approval_status IN ('Pending','Approved').

A Cancelled COA does not block a new submission for the same employee/date. The user can re-submit after a cancellation.

3.3 Approving a COA – approve()

When a Pending COA is approved:

  1. Sets approval_status = 'Approved'.
  2. Creates a new attendance_records row with:
    • attendance_area = 'COA' (marks the record as coming from a certificate)
    • record_date, earliest_time, latest_time from the COA
    • biometric_imports_id from the current active import
  3. Saves the generated attendance_records.id back to certificate_attendance.attendance_records_id.
  4. Still calls a Python script (attendance_manager.py add ...) to compute overtime for the new record. This Python call has not yet been converted to PHP.
Known gap: The OT computation for COA approvals still runs through Python. After the Python call is converted, it should use ComputationService::autocalculateOrd() and logOvertimeDb() in the same way as OvertimeController@updateTime().

3.4 Cancelling a COA – cancel()

  • Sets approval_status = 'Cancelled'.
  • Does not delete the linked attendance_records row or the overtimes row.

3.5 Finalizing via JSON batch – AttendanceProcessor@finalizeCertificates()

Used by CsvimportController@finalizeAttendanceCertificates() to process a batch JSON file (attendance_certificates.json). Each entry has an action field:

actionLogic
addIf no attendance_record exists for employee + date → insert one (with COA times)
removeDeletes the attendance_record AND the linked overtime record for employee + date

4. Leaves

Controller: LeaveController
Table: leaves

4.1 Purpose

Leaves track employee absences. When a leave is recorded and applied to the attendance computation, the employee's attendance row is flagged (leaves = true), which causes the OT calculation to return all zeros (no overtime is earned on a leave day).

4.2 Status Values

Important: Leave statuses are lowercase: 'pending', 'approved', 'cancelled'. All other modules use Title Case ('Pending', 'Approved', 'Cancelled'). Any comparison code must use the correct case for this table.

4.3 Creating Leaves – store()

Accepts an array of items (leaveArray).

  • Each item must have: employee_management_id, record_date, leave_type.
  • Optional fields: reason, with_pay (defaults to 'No'), status (defaults to 'pending').

Duplicate check

Before creating, checks for an existing leave for the same employee_management_id + biometric_imports_id + record_date with status pending or approved.

  • If found → adds to skipped list, continues to next item.
  • If only a cancelled leave exists → creation is allowed.

Response includes created_count and the list of skipped records.

4.4 Approving a Leave – approve()

  • Finds the leave by ID.
  • Sets status = 'approved'.
  • No further side effects (does not update attendance_records.leaves automatically).
Note: The attendance_records.leaves flag may need to be set separately for the OT exclusion to take effect. Verify whether there is a separate process that propagates the approved leave flag to attendance_records.

4.5 Cancelling a Leave – cancel()

  • Sets status = 'cancelled'.
  • No other changes (does not re-enable OT for the day).

4.6 Leave Fields Stored

4.7 How Leaves Affect OT

In autocalculateOrd() and autocalculateRdAndOvertime(), the check is:

This means if the attendance row is flagged as a leave day, zero overtime is computed regardless of the punch times.

5. Schedule Adjustment

Controller: ScheduleAdjustmentController
Service: ComputationService@adjustShiftWithSnapshot
Table: schedule_adjustments

5.1 Purpose

A Schedule Adjustment allows a manager to change an employee's assigned shift for a specific date (e.g., move from a day shift to a night shift). When approved, the system recalculates overtime using the new schedule and preserves a snapshot of the original OT values for audit purposes.

5.2 Creating a Schedule Adjustment – store()

  • Required fields per item: employee_management_id, record_date, schedule.
  • Optional: others, reason, approval_status (defaults to 'Pending').
  • Duplicate check: blocks creation if a Pending or Approved record already exists for employee_management_id + record_date + biometric_imports_id.
  • Automatically looks up the attendance_records.id for the same employee + date and stores it as attendance_records_id (can be null if no attendance record exists yet).

5.3 Approving a Schedule Adjustment – approve()

This is the most complex workflow in the module. The steps are:

Step 1 – Set approval status

$scheduleAdjustment->approval_status = 'Approved';
$scheduleAdjustment->save();

Step 2 – Load related records

  • Loads the linked attendance_records row.
  • Loads the linked employee_management row.
  • Loads the existing overtimes row (may be null if none exists yet).

Step 3 – Snapshot + midnight-safe recalculation

adjustShiftWithSnapshot() is called. This method:

  1. Snapshot: Writes the current (original) overtime values to storage/app/schedule_adjustment_snapshots.json before making any changes. The snapshot uses a reference key in the format SNAP-{attendance_records_id}-{timestamp}.
  2. Parse schedule: Splits the new schedule string (e.g. '19-7') into start hour (19) and end hour (7).
  3. Midnight crossing fix: Builds full Carbon datetimes so that night shifts produce a positive duration: 
    startDt = Carbon::parse("{record_date} {startHour}:00:00")
endDt   = Carbon::parse("{record_date} {endHour}:00:00")
if endDt ≤ startDt → endDt.addDay()  // 19→7 on same date would be -12h; now +12h
  4. Duration: If actual punch times are available, uses those instead of schedule hours (more precise). Handles punch-out midnight crossing the same way.
  5. OT calculation: 
    otHours = max(duration_hours - 8, 0)
    Returns 0 if the shift is ≤ 8 hours.

Step 4 – Full ND/RD breakdown

After adjustShiftWithSnapshot() returns the corrected times, the controller calls:

  • autocalculateOrd() with the midnight-safe times → produces ordOt, ordNd, ordNdOt.
  • autocalculateRdAndOvertime() → produces rd, rd_ot, rd_nd, rd_nd_ot.

Step 5 – Persist new OT

logOvertimeDb() upserts the result into the overtimes table. The new OT is saved with status = 'Pending' so it still requires approval in the Overtime module.

Response payload

The API response includes:

FieldContent
adjustedNew schedule, times, duration_hours, ot_hours, ot_formatted, crosses_midnight, standard_hours
snapshot_refKey string to locate the original in the JSON snapshot file
original_otOriginal ord_ot, ord_nd, ord_nd_ot, rd, rd_ot, rd_nd, rd_nd_ot values

5.4 Cancelling a Schedule Adjustment – cancel()

  • Sets approval_status = 'Cancelled'.
  • Does not revert the overtime record or remove the snapshot.

5.5 Night Shift Codes

The following schedule codes are recognized as night shifts (midnight-crossing is expected):

18-6, 19-7, 19-4, 20-5, 15-23, 15-24, 23-7, 23-8

5.6 How Schedule Adjustments Affect autocalculateOrd()

In both autocalculateOrd() and autocalculateRdAndOvertime(), schedule adjustments are checked first (higher priority than the employee's default schedule). This means the temp schedule for the specific date overrides the master schedule.

6.4 Duplicate Prevention

No two records can share the same combination of:

employee_management_id + record_date + earliest_time + latest_time + weekday + biometric_imports_id

Duplicate rows are silently skipped during batch import (not an error).

6.5 Records Where earliest_time = latest_time

These are skipped at insert time. A single biometric punch (no paired in/out) cannot produce a meaningful attendance record. The row is counted in skipped_same_time in the import statistics.

6.6 Biometric Import Sessions

The biometric_imports table tracks upload batches. The record with status = 'load' is the active/current session. All new attendance records are associated with this import ID. The model BiometricHistoryList provides the helper getLoadedRecordId() which returns this ID for use by all controllers.
